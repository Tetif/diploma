# Анализ причин плохих результатов моделей и возможные решения

## 1. PyTorch-модели (нейросети)

### 1.1 Регрессия: катастрофические MAE/R² (Housing, Wine)

**Наблюдения:**
- **Housing**: MAE ~207 000, R² ≈ -3.2 при целевом `median_house_value` (порядка 50 000–500 000).
- **Wine**: MAE 1.7–4.4, R² от -5 до -34 при целевом `quality` (обычно 3–8).
- **Zillow**: R² ≈ 0 при целевом `logerror` (уже в диапазоне порядка ±0.5).

**Причины:**

1. **Отсутствие масштабирования целевой переменной (Housing, Wine)**  
   Нейросеть обучается с `MSELoss` на сырых значениях. При `median_house_value` порядка 100 000–300 000:
   - выходы слоёв при инициализации имеют порядок единиц;
   - градиенты по MSE огромные, обучение нестабильно;
   - модель либо расходится, либо сходится к предсказанию константы (например, среднего), что даёт очень высокий MAE и отрицательный R².

2. **Тот же MSE на немасштабированной цели (Wine)**  
   Даже при меньшем диапазоне (3–8) оптимизация без нормализации цели и без подходящего learning rate часто даёт предсказания хуже среднего (R² < 0).

3. **Zillow**  
   `logerror` уже в разумном масштабе, но R² ≈ 0 указывает на то, что задача сложная (слабая предсказуемость по текущим признакам) или не хватает ёмкости/регуляризации/эпох.

**Решения:**

| Решение | Описание |
|--------|----------|
| **Масштабирование целевой переменной** | Для регрессии при обучении PyTorch: обучать на `y_scaled = StandardScaler().fit_transform(y.reshape(-1,1))`, предсказания переводить обратно: `y_pred = scaler.inverse_transform(model(X))`. Метрики (MAE, RMSE, R²) считать по исходной шкале. |
| **Learning rate и эпохи** | После масштабирования цели попробовать lr=1e-3, 500–1000 эпох; при необходимости early stopping по val loss. |
| **Zillow** | Помимо масштабирования: больше эпох, feature engineering, проверка качества признаков и целевой переменной. |

### 1.2 Классификация (Adult): «все в один класс», низкий Accuracy

**Наблюдения:**
- Accuracy 0.36–0.51, Recall ≈ 0.99, Precision ≈ 0.27–0.33.
- Модель по сути предсказывает класс 1 почти для всех объектов.

**Причины:**

1. **Использование MSELoss вместо BCE**  
   Сейчас модель регрессирует один выход на метки 0/1. Для бинарной классификации корректнее:
   - один выход как **логит**;
   - функция потерь **BCEWithLogitsLoss** (или BCELoss после sigmoid).

2. **Дисбаланс классов (Adult ~24% положительный класс)**  
   При MSE модель может «уйти» в сторону предсказания одного класса. При BCE можно задать `pos_weight` для увеличения веса положительного класса и получить более сбалансированные предсказания.

3. **Инициализация и ReLU**  
   Нелинейности и инициализация могут давать систематически положительные выходы → после условного порога 0.5 почти все объекты попадают в класс 1 → высокий recall, низкий precision.

**Решения:**

| Решение | Описание |
|--------|----------|
| **BCEWithLogitsLoss** | Вместо MSELoss использовать `nn.BCEWithLogitsLoss()`. На выходе сети — один нейрон (логит); при предсказании применять `sigmoid` для вероятности и порог 0.5 для класса. |
| **Вес положительного класса** | `pos_weight = (count_neg / count_pos)` для датасета (или подвыборки), чтобы компенсировать дисбаланс. |
| **Порог по умолчанию** | Оставить 0.5 или подобрать по F1/ROC-AUC на валидации. |

## 2. Деревья решений: переобучение (Wine, отчасти Housing)

**Наблюдения:**
- **Wine** (малый датасет): LightGBM, XGBoost, Random Forest — Train R² 0.73–0.80, Test R² 0.40–0.45; разрыв большой.
- **Housing**: Random Forest — Train MAE 24 797, Test MAE 33 590 (~+35%).

**Причины:**
- Малая выборка (Wine) или избыточная сложность модели (глубина, число деревьев) без достаточной регуляризации.
- Случайный лес часто сильнее переобучается при малом объёме данных.

**Решения:**

| Решение | Описание |
|--------|----------|
| **Регуляризация** | Уменьшить `max_depth`, увеличить `min_samples_leaf` / `min_data_in_leaf`, уменьшить `n_estimators` для Wine. |
| **Ранняя остановка** | Для LightGBM/XGBoost использовать early stopping по валидационной выборке (уже есть в основном пайплайне). |
| **Кросс-валидация** | Подбор гиперпараметров по CV, а не по одному train/test. |

## 3. Zillow: все модели дают R² ≈ 0

**Наблюдения:**
- Деревья и нейросети: Test R² от -0.02 до 0.006.
- Целевая переменная — `logerror`, масштаб уже небольшой.

**Причины:**
- **Сложность задачи**: logerror слабо предсказуем по имеющимся признакам.
- **Качество/полнота признаков**: много пропусков, нужен аккуратный feature engineering.
- **Целевая переменная**: возможен шум, выбросы, нестационарность по времени.

**Решения:**

| Решение | Описание |
|--------|----------|
| **Feature engineering** | Агрегаты, временные признаки, обработка пропусков, отбор признаков. |
| **Анализ целевой** | Распределение logerror, выбросы, связь с датой транзакции. |
| **Ансамбли и тюнинг** | Более тщательный подбор моделей и гиперпараметров после улучшения признаков. |
| **Упрощение задачи** | Предсказание бинарного/категориального таргета (например, знак logerror) для проверки предсказуемости. |

## 4. Сводка изменений в коде (реализовано)

В проекте внесены следующие изменения:

1. **Регрессия PyTorch в `check_overfitting.py`**  
   Для PyTorch при регрессии целевая переменная масштабируется через `StandardScaler` по обучающей выборке; предсказания преобразуются обратно перед вычислением MAE/RMSE/R².

2. **Классификация PyTorch**  
   В `PyTorchModelWrapper` добавлена поддержка `task_type='binary_classification'`: используется `BCEWithLogitsLoss`, при предсказании к выходу применяется sigmoid; при создании модели из `check_overfitting` передаётся `task_type` и при дисбалансе задаётся `pos_weight = n_neg / n_pos`.

### Проверка после правок

- **Adult, pytorch_simple**: Accuracy **0.82** (train) / **0.81** (test), F1 **0.71/0.68** (раньше ~0.50 и «все в класс 1»).
- **Housing, pytorch_simple**: MAE **43k/44k**, R² **0.73/0.71** (раньше MAE ~207k, R² ≈ -3.2).

После этих правок имеет смысл заново прогнать `check_overfitting.py --all` по всем датасетам и моделям и обновить отчёт по переобучению.
